# Maintaining the statutory layer

How to keep the statutory enrichment current, and the rules that keep it honest.

## What the layer is

The 953-record corpus in `src/data/offense-codes.json` is a frozen extraction of the February 2024 Illinois Secretary of State Police Offense Code Index. **It is never edited.** Its SHA-256 is pinned in `config/source-version.json` and asserted by the release validator; those bytes are the evidence that the source publication said what we say it said.

Everything about *current* law lives in a separate layer keyed to that corpus:

| Path | What it holds | Generated by |
| --- | --- | --- |
| `content/mappings/citation-overrides.json` | Hand-mapped citations, with evidence. **Hand-maintained.** | you |
| `src/data/enrichment/citation-model.json` | Chapter/act/section for all 953 records | `build-citation-model.mjs` |
| `src/data/enrichment/sections/*.json` | Statutory text + provenance, one per section | `verify-ilga.mjs` |
| `src/data/enrichment/manifest.json` | Per-record status after the last sweep | `verify-ilga.mjs` |
| `src/data/lookup-index.json` | The runtime payload (derived, gitignored) | `build-lookup-index.mjs` |
| `docs/illinois-law-audit.md` | Findings report | `report-audit.mjs` |
| `content/drafts/*.json` | Generated prose. **Never shipped.** | a human, reviewed |
| `content/review-log.ndjson` | Hash-chained review signatures | a human, appended |

## Routine sweep

```bash
npm run enrichment:probe
```

Confirms ILGA's URL template still works. Run it first; it is cheap and it fails loudly when ILGA moves the path, which it has done before. The legacy `fulltext.asp` form returned 404 for every section on 2026-08-17. If the probe fails, do not sweep — fix the template in `config/enrichment-version.json` first.

```bash
npm run enrichment:verify
```

Fetches every section behind the corpus, one request at a time with a 1.5s gap, using cached copies and conditional requests where possible. A cold run takes about 18 minutes; a warm one is seconds. **Exits non-zero when statutory text has changed since the last sweep**, and writes the diff to `content/review-queue/statutory-changes.json`. It never republishes anything on its own.

```bash
npm run enrichment:audit
```

Regenerates `docs/illinois-law-audit.md`.

Useful flags: `--offline` (cache only), `--refresh` (ignore cache), `--limit=25` (iterate quickly).

## Reading the statuses

Section status describes **what was retrieved**, never whether it is legally correct.

- `retrieved` — ILGA served the section and echoed the citation requested.
- `repealed` — served, and the text is marked repealed.
- `unavailable` — ILGA served its "not currently available" notice.
- `citation-mismatch` — ILGA returned a different section. Treat as unresolved.
- `subsection-not-found` — section retrieved, but the cited subsection is gone.
- `fetch-failed` — transport failure. Not a finding about the law; re-run.

The word **`verified` is deliberately absent.** It is reserved for a recorded human review, which nothing in this pipeline performs.

## Two traps worth knowing

**ILGA answers HTTP 200 for sections that do not exist.** Status codes are not a validity signal. Validity is established by the citation echoed in the embedded document title, and by the absence of the "not currently available" sentinel. If this check ever regresses, nonexistent sections get stored as though they were real law. `test/ilga-extract.test.mjs` covers it.

**An `unavailable` result is not proof of repeal.** It often means the source publication's citation format does not match ILGA's. The first sweep reported 16 unavailable sections; nine of them were `625 ILCS 40/5-1A` through `5-1L`, which are the lettered subsections of `625 ILCS 40/5-1` ("Operation Generally") written without parentheses. They were live law the whole time. Always check whether the base section exists before recording a repeal.

## Adding an override

When a citation cannot be resolved automatically, map it in `content/mappings/citation-overrides.json` — the resolver reads this file and never writes to it. Every mapped entry must carry `evidence`: the canonical citation, the section heading text, the ILGA URL it came from, and the date checked. `test/citation-model.test.mjs` fails the build if any override lacks evidence.

**An override without evidence is a guess, and a guess about which statute an officer is looking at is the exact failure this project exists to prevent.** Where the right mapping is genuinely unclear, leave the record unresolved so it stays visible in the audit, rather than inventing one.

## Reviewing generated content

Nothing generated is published without a recorded human review, and the review binds to
**specific bytes** rather than to a record name:

```bash
npm run enrichment:validate
```

- Drafts live in `content/drafts/` and are never copied into `dist/`.
- `content/review-log.ndjson` is an append-only hash chain. Each entry records
  `draftSha256` (the exact text a person read) and `sectionSha256` (the exact statutory
  text it was derived from), plus `prev` linking to the entry before it.
- Edit an approved draft, or let Illinois amend the statute beneath it, and the hashes
  stop matching — the record silently returns to needs-review. **An approval cannot be
  inherited by content nobody approved.**
- Every quick element must carry a `sourceMapping` whose `sourceText` is a *verbatim
  substring* of that section's retrieved text. An element that cannot be anchored fails
  the build. This is what makes "traceable to source" an assertion rather than a promise.
- Reordering or deleting log entries breaks the chain and is reported.

The latest decision for a record wins, so an approval can be withdrawn later without
rewriting history.

## What the pipeline cannot do

- It does not confirm a record's description still matches the section it cites. That is a reading task.
- It does not retrieve classification, penalties, or court-appearance consequences.
- It cannot detect an amendment that changed meaning without changing the Public Act line.
- It cannot mark anything `verified`. Only a recorded human review can. That mechanism now exists (`content/review-log.ndjson`, hash-chained to specific bytes) but no record has been reviewed, so nothing is publishable.

`config/enrichment-version.json` carries `review.humanReviewedRecordCount: 0`. Raising it without a review log fails the release validator by design — see `test/release-governance.test.mjs`.

## Guardrails in the release validator

`scripts/validate-release.mjs` rejects a release when the enrichment layer:

- references a different corpus than the one shipped,
- contains a record id the corpus does not have,
- claims human review without a review log,
- or fails to disclaim government affiliation.

The layer is optional throughout: with no enrichment on disk the site builds and degrades to the frozen corpus.
